# Yeet mode

“Yeet process issues” works on its own. When the user gives an observable outcome, prefer eligible issues that most directly deliver or unblock it. Treat a stated scope boundary as a limit on selection. For example, “A user can preview a CSV, correct a row and retry without duplicates. Billing changes are out of scope.” Both details are optional. Start from the repository backlog when neither is supplied.

## Run the queue

Record the UTC start and the deadline exactly 12 elapsed hours later in the run ledger. Carry both through handoffs, retries and context compaction. Before every admission, read the clock and check available issue slots. Refill up to three concurrent issues while time remains. Preserve explicit issue lists, lane boundaries, repository protections and existing ownership.

Inventory all open issues in scope, including earlier blocked issues and items without a primary state. Triage each under the usual eligibility rules. On startup and after a merge or decision, revisit affected blockers against the current default branch. Resolve stale assumptions and reversible design choices, clear obsolete labels and claim newly eligible issues. Follow the normal state policy for hard dependencies, reserved work and explicit human decisions.

Continue while eligible work or a pending event the agent can monitor could advance the run. When a refresh finds only genuine external or human handoffs, record each disposition and end the run. At the deadline, tell the user the 12-hour limit was reached, freeze the set of admitted issues, and finish their implementation, corrections, reviews and qualifying merges. Do not claim a new issue after cutoff, even when a finishing merge unlocks it. If a service fails or a human gate prevents completion, preserve the work and report the precise handoff. Report what merged, what is still open and what became ready after cutoff.

## Keep the PR Review Hub current

For every opted-in repository, the primary maintainer updates its private Hub during the run. Use the [existing publisher and receipt checks](review-site-publication.md#publish-and-retain-a-receipt). Workers report milestones to the maintainer, who serializes updates per PR and can publish different PRs independently. Use the configured Hub publishing interface for these writes. The ban on writes to project production databases still applies to all implementation and testing.

- **First draft.** The Hub is keyed by PR number. Track pre-PR work on its GitHub issue. Once a real scoped commit is pushed, open or reuse its draft PR and publish its first checkpoint. Include the issue, the current goal, what has landed on the branch and the next step. Use the actual clean revision and mark outstanding criteria and demonstrations `not verified`. A progress entry may precede the normal final-evidence window, including on repositories with optional final evidence.
- **During work.** Publish when a material implementation step lands, verification passes or fails, a blocker or assumption changes, or human input is needed. Refresh at ready-for-review, at the independent and GitHub review outcomes, and when entering a merge queue. In the visible summary, name the current stage, what was verified for this SHA, and the next action or decision and its owner. Read checks and reviews from GitHub for the current SHA. Include the observed result and time in the summary when the publisher's status fields report unknown.
- **On disposition.** Refresh after a verified merge, closure or handoff. At cutoff reconcile entries for the issues still underway, then continue updating them as they finish. Before the final report, check each affected PR's last delivered milestone against GitHub. Report any outstanding delivery and the last verified Hub link. Honor opted-in cleanup of merged entries.
- **Delivery.** Skip unchanged polls. Reuse the existing finalized bundle for observation-only changes such as draft or merge state. Publish a revised bundle when the visible summary, decision or evidence changes. Keep capture provenance and timestamps accurate, retain verified evidence for its original SHA, and label gaps on a newer head. Verify the receipt identifies the expected current publication and read back the displayed milestone. Reconcile historical or conflicting receipts before claiming the update. If delivery fails, keep the latest pending update per PR locally, retry at the next milestone and final reconciliation, and continue independent work. Required final evidence still gates readiness.

## Make and record decisions

For a blocker requiring a choice, ask a subagent for three viable options with trade-offs, evidence and a recommendation. As primary maintainer, select the best authorized option against acceptance criteria, existing reusable components, maintenance cost, reversibility and testability. Verify the assumption in the smallest representative environment. Carry on with that choice. If a human must decide, give the same options and recommendation and continue independent issues.

Record each resolved blocker decision once in a comment on the affected issue and once on its PR (backfill when the PR opens). State the assumption, chosen option and reason, both alternatives, and what evidence would warrant switching. Include the same decision and alternatives in the opted-in PR Review Hub entry using its existing summary fields and link the durable records where possible. Update existing records on retry. Respect visibility and disclosure rules. If hub delivery is unavailable, record the outstanding delivery and surface it in the final report. If the hub is opted out, retain the GitHub records and respect that choice.

When a human preference creates a concrete maintenance, performance or safety cost, explain the trade-off respectfully and use Ponytail Review, when installed, to propose an alternative. Follow the human's permissible choice and keep moving.

## Review and merge

1. At meaningful checkpoints on a complex issue or large diff, run the installed `ponytail-review` skill, for example after the core design is testable and again when later changes affect its conclusions. Ask for security, application performance under realistic load, and general engineering practices, including component reuse. If unavailable, continue with independent subagent review and distinguish that review in the evidence.
2. Use a subagent other than the implementer to review each routine PR. Give it the diff, acceptance criteria, test evidence and current head SHA. Require a verdict and findings tied to that SHA. Keep work needing serious human judgment in human review, including unresolved product intent, significant security or data loss trade-offs, and mandatory owner approvals. An agent verdict does not satisfy a required GitHub human approval.
3. Request or verify the repository's configured GitHub code review for this head. Monitor for a completed review covering the current revision, inspect its findings and resolve actionable feedback using the normal correction and ready-window rules. Green CI, a queued request, silence or a review of an older SHA cannot establish completion. If the GitHub review service is unavailable or no reviewer is configured, record the exact missing gate and continue other work. Treat a pending healthy review as ongoing work.
4. Before merging, verify the PR is in scope, authorized for this run, targets the intended default branch and is ready. Require a passing independent review, completed GitHub code review, required checks and approvals, the clean ready window, required acceptance evidence, resolved blockers and no outstanding human action. Refresh reviews, comments, checks and head immediately before merge. A changed head requires fresh review and relevant verification. The primary maintainer merges using the repository's normal method with the reviewed head as an expected-SHA guard. Respect merge queues and branch protections. Never use an admin bypass.
5. Verify the merge on GitHub and that the result reached the remote default branch before recording success, confirming issue closure or unblocking dependents. If queued, monitor the result. Reconcile uncertain responses before retrying and honor the existing correction limits.

## Database isolation

Yeet mode prohibits production database writes, including migrations, setup, seeds, cleanup, integrations and indirect writes from tests or merge-triggered deployment. Verify the target and downstream effects before running a write-capable path or merging a PR that could trigger one. Exercise it in a disposable local database, simulator or virtual environment with synthetic data and isolated endpoints and credentials. If an unavoidable production write is part of acceptance or deployment, finish the isolated work, record exactly what was verified, and leave that action or merge for a human.
